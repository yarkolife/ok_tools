# Internationalization (i18n) Guide

> **Version:** 1.0  
> **Last Updated:** 2025-01-15  
> **Status:** Complete

This document describes how to manage translations in OK Tools project.

## Overview

OK Tools uses Django's internationalization (i18n) system with a **hybrid approach**:
- **Project-level translations** in `ok_tools/locale/` for shared/cross-app strings
- **Per-app translations** in `APP/locale/` for domain-specific strings

## Supported Languages

Currently supported: **German (de)** only.

## Translation File Structure

### Project-level translations
- Location: `ok_tools/locale/de/LC_MESSAGES/`
- Files: `django.po`, `djangojs.po`
- Contains: Shared strings, core templates, common UI elements

### Per-app translations
The following apps have their own `locale/` directories:

- `dashboard/locale/de/LC_MESSAGES/` - Dashboard widgets and analytics
- `planung/locale/de/LC_MESSAGES/` - Planning/calendar functionality (includes `djangojs.po`)
- `rental/locale/de/LC_MESSAGES/` - Rental system UI and emails (includes `djangojs.po`)
- `media_files/locale/de/LC_MESSAGES/` - Media file management admin interface
- `licenses/locale/de/LC_MESSAGES/` - License management templates

## Updating Translations

### Automated Workflow

Use the provided script to update all translation files at once:

#### Development (docker-local)

**Important:** Run from project root directory (`/Users/pavlo/coding/ok_tools_v3`):

```bash
# From project root
docker compose -f docker-local/docker-compose.yml exec web bash -lc '/app/scripts/i18n_update.sh'
```

Or if you're already in `docker-local/` directory:

```bash
# From docker-local/ directory
docker compose exec web bash -lc '/app/scripts/i18n_update.sh'
```

#### Production (from `../ok_tools_production`)

```bash
cd ../ok_tools_production
docker compose exec web bash -lc '/app/scripts/i18n_update.sh'
```

### What the Script Does

1. **Updates `django.po` files** for each app:
   - `ok_tools/`
   - `dashboard/`
   - `planung/`
   - `rental/`
   - `media_files/`
   - `licenses/`

2. **Updates `djangojs.po` files** for apps with JavaScript translations:
   - `ok_tools/`
   - `planung/`
   - `rental/`

3. **Compiles all messages** to `.mo` files for runtime use

### Manual Workflow (if needed)

If you need to update translations for a specific app only:

```bash
# Inside Docker container
cd /app/rental  # or any other app
python ../manage.py makemessages -l de -d django
python ../manage.py makemessages -l de -d djangojs  # if app has JS translations
python ../manage.py compilemessages -l de
```

## Translation Workflow

### Adding New Translatable Strings

1. **In Python code:**
   ```python
   from django.utils.translation import gettext_lazy as _
   
   class MyModel(models.Model):
       name = models.CharField(_("Name"), max_length=100)
   ```

2. **In templates:**
   ```django
   {% load i18n %}
   {% trans "Welcome" %}
   ```

3. **In JavaScript (if app has djangojs.po):**
   ```javascript
   // Use gettext() function (loaded via {% load i18n %} in template)
   const text = gettext("Save");
   ```

### Updating Translation Files

1. Run the update script (see above)
2. Edit `.po` files in your editor or translation tool (e.g., Poedit)
3. Run the script again to compile messages

### Best Practices

- **Use context** (`pgettext`) if the same English string needs different translations in different contexts
- **Keep translations close to code** - per-app `locale/` directories help with this
- **Don't manually move strings** between translation files - let `makemessages` handle it
- **Review duplicate `msgid` entries** - if same string needs different translations, use context

## Compilation (.mo files)

`.mo` files are binary compiled versions of `.po` files that Django uses at runtime. They are created from `.po` files using the `compilemessages` command.

### Automatic Compilation

Translation files are automatically compiled during:
- **Production deployment** (via `entrypoint.production.sh` - runs `compilemessages` on container startup)
- **Celery worker startup** (via `entrypoint.celery.sh` - runs `compilemessages` on container startup)
- **Script execution** (via `i18n_update.sh` - compiles after updating .po files)

### Why Celery compilation matters for emails

License notification emails are rendered in Celery tasks (not in the web request cycle).
If the worker container starts without fresh `.mo` files, email templates can fall back
to English `msgid` strings even when German translations exist in `.po` files.

The production setup now compiles translations in both entrypoints:
- [`deployment/entrypoint.production.sh`](deployment/entrypoint.production.sh:22)
- [`deployment/entrypoint.celery.sh`](deployment/entrypoint.celery.sh:1)

This keeps email rendering consistent with organization language settings.

### Manual Compilation

#### Development (docker-local)

```bash
# From docker-local/ directory
docker compose exec web python manage.py compilemessages -l de

# Or from project root
docker compose -f docker-local/docker-compose.yml exec web python manage.py compilemessages -l de
```

#### Production (from `../ok_tools_production`)

```bash
cd ../ok_tools_production
docker compose exec web python manage.py compilemessages -l de
```

**Note:** After editing `.po` files, you must run `compilemessages` for changes to take effect. Django reads `.mo` files at runtime, not `.po` files.

For production deployments, restart both web and Celery services after translation updates so both containers load fresh catalogs.

## Copying Existing Translations

When creating new per-app locale files, you can copy translations from the old `ok_tools/locale/django.po` file:

```bash
# From project root
python3 scripts/i18n_copy_translations.py
```

This script:
- Finds matching `msgid` entries in new per-app `.po` files
- Copies `msgstr` translations from `ok_tools/locale/django.po`
- Only updates empty `msgstr` entries (doesn't overwrite existing translations)

**Note:** Most strings are app-specific, so only common strings (like "Description", "Status", etc.) will be copied.

## Checking Translation Status

To check which strings still need translation:

```bash
# From project root (outside Docker)
./scripts/i18n_check_untranslated.sh

# Or check specific app
./scripts/i18n_check_untranslated.sh rental
```

The script shows:
- Number of translated vs untranslated strings per app
- Overall translation percentage
- Exit code 0 if all translated, 1 if any untranslated

## Troubleshooting

### Translation not appearing

1. Check that string is wrapped with `_()` or `{% trans %}`
2. Run `makemessages` to update `.po` files
3. Add/update translation in `.po` file
4. Run `compilemessages` to generate `.mo` files
5. Restart Django application

### Missing locale directory

The script automatically creates `locale/de/LC_MESSAGES/` directories if they don't exist. No manual setup needed.

### JavaScript translations not working

1. Ensure app has `djangojs.po` file
2. Check that `{% load i18n %}` is in template
3. Verify `gettext()` function is available in JavaScript context
4. Recompile messages after updating `djangojs.po`

## Configuration

Translation settings are configured in `ok_tools/settings.py`:

- `USE_I18N = True` - Enables internationalization
- `LOCALE_PATHS = [BASE_DIR / "ok_tools/locale"]` - Project-level translations
- `LANGUAGE_CODE` - Default language (from `I18N_DEFAULT_LANGUAGE` env var)
- `LANGUAGES` - Supported languages (from `I18N_SUPPORTED_LANGUAGES` env var)

Language selection is handled by:
- `ForceDefaultLanguageMiddleware` - Sets default language in session
- `LocaleMiddleware` - Activates language based on session/cookie/header
